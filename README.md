# Запись в парикмахерскую — MVP

Next.js 14 (App Router) + TypeScript + PostgreSQL + Prisma. Один язык (TypeScript) на фронт и бэк, разворачивается на любом VPS через Docker.

## Что реализовано

Главная страница теперь — просто две кнопки: "Регистрация" и "Вход", всё остальное (запись, отмена, история) происходит уже внутри личного кабинета клиента. Регистрация (`/register`): телефон, имя, пароль, подтверждение пароля — после неё клиент сразу авторизован и попадает в свой календарь (`/calendar`). Вход (`/login`) — телефон и пароль (для клиента; email+пароль для админа, телефон+пароль для мастера — форма одна на всех, см. ниже). Сессия настоящая и общая для всего клиентского раздела: `/calendar` и `/cabinet` сразу показывают данные вошедшего клиента, повторно логиниться не нужно, пока сессия жива (защищена middleware, как у админа и мастера). Личный кабинет (`/cabinet`, кнопка "Список" из `/calendar`, а также кнопка-домик "На главную" в шапке): история записей, отмена, счётчик бонусов. Старый анонимный визард `/booking` (без регистрации, только имя+телефон) по-прежнему работает как отдельный вход для тех, кто пришёл по прямой ссылке, но с главной страницы на него ссылок больше нет. Весь клиентский интерфейс (лендинг, регистрация, вход, календарь, кабинет) сделан только под мобильный экран — фиксированная узкая колонка, крупные кнопки под палец, без десктопной раскладки.

Цена услуги необязательна: при создании услуги в админке поле "Цена" можно оставить пустым, тогда она нигде не показывается (ни в записи, ни в списке услуг) — заполняется только длительность.

Вход один на всех — `/login`, форма одна (телефон/email + пароль), сервер сам решает, кто пришёл: email, совпавший с админом → пускает в `/admin/calendar`; телефон, совпавший с мастером → пускает в `/master/calendar`; телефон зарегистрированного клиента → пускает в `/calendar`. Клиент должен сначала зарегистрироваться на `/register` (пароль обязателен для всех ролей теперь, включая клиента). Старые `/admin/login` и `/master/login` теперь просто редиректят на `/login`.

Для администратора: календарь на день по всем мастерам одновременно, создание записи вручную (по звонку), управление услугами и мастерами (включая недельный график работы каждого — кнопка "График" у мастера: чекбокс рабочий/выходной день + время начала-конца по каждому дню недели). Дата в календаре выбирается через мини-календарь (не системный date-picker): дни с хотя бы одной записью подсвечены зелёным, а прошедшие дни с записями — серым. Отдельная страница "Очередь" (`/admin/waitlist`) — журнал клиентов, для которых не нашлось свободного времени: список в порядке очереди (FIFO), кнопка "Записать" открывает подбор мастера/даты/времени и создаёт запись по данным этого клиента, кнопка "Убрать" — просто снимает с очереди. Страница "Клиенты" (`/admin/clients`, только у админа, мастеру не видна) — список всех зарегистрированных клиентов с телефоном, количеством записей и бонусами; бонусы можно поправить вручную ("Изменить" → ввести число → "Сохранить"), клиента можно удалить целиком — вместе с ним каскадно удаляются его записи и очередь ожидания, действие необратимо.

Для мастера: тот же общий календарь по всем мастерам и та же очередь, что и у админа, может создавать записи и записывать из очереди, но удалить может только записи, которые ещё не наступили — прошедшие записи трогать нельзя (только администратор). Клик по записи в календаре открывает окно с деталями (имя, телефон, услуга, мастер, время, статус); кнопка "Удалить" внутри него требует дополнительного подтверждения.

Календарь клиента на `/calendar` (после входа): та же сетка по мастерам на день, но с защитой приватности — чужие записи видны только как безликие блоки "Занято" (без имени, телефона, услуги), а свои — выделены цветом и кликабельны (показывают детали и кнопки "Перенести"/"Отменить"). Клик по свободной ячейке у мастера открывает выбор услуги и свободного времени и сразу создаёт запись — записаться и отменить запись можно прямо через календарь.

Перенос записи (кнопка "Перенести" рядом с "Отменить"/"Удалить" — в личном кабинете, в клиентском календаре и в общем календаре админа/мастера): выбирается новая дата и время из реально свободных слотов того же мастера (или другого — см. ниже), затем запись обновляется одной операцией внутри транзакции с повторной проверкой занятости слота (та же защита от двойной записи, что и при создании, только с исключением самой переносимой записи, чтобы она не конфликтовала сама с собой). Клиент может перенести свою запись на другого мастера, другую дату и время — выбор мастера ограничен только теми, кто выполняет ту же услугу. Админ может перенести любую запись на любого мастера/дату/время. Мастер может перенести дату и время, но не может переназначить запись другому мастеру (сервер вернёт 403) — это осознанно оставлено только админу; ограничение "нельзя трогать прошедшие записи" для мастера действует и здесь.

Автоочистка старых записей: отдельный процесс `scheduler` (см. `docker-compose.yml`, `scripts/scheduler.ts`) каждое воскресенье в 00:00 (время сервера, настраивается через `TZ` в `.env`/`docker-compose.yml`; расписание — через `PURGE_CRON`, по умолчанию `"0 0 * * 0"`) находит все записи, которые уже закончились (`endAt < сейчас`), и **безвозвратно удаляет** их из таблицы `Appointment`. Будущие записи (и текущие, которые ещё не закончились) не трогает. Никакой истории нигде не сохраняется — это осознанное решение по вашей просьбе. Лог самой работы джобы (сколько записей удалено и когда) виден в докер-логах контейнера `hairdresser-booking-scheduler` (`docker compose logs -f scheduler`). Ручной запуск для проверки/тестирования — `npm run purge:run` (или `docker compose exec scheduler npx tsx scripts/purge-once.ts` в проде).

Ограничение "один мастер в день": клиент не может в один и тот же календарный день записаться к двум разным мастерам (только к одному, можно несколько услуг подряд у него же) — проверяется при создании записи и при переносе, и на бэкенде, и это касается только самостоятельной записи клиента (админ/мастер при ручном создании записи это ограничение не затрагивает). Список услуг в окне записи (клиентский календарь и админский календарь) теперь фильтруется по конкретному мастеру, на которого кликнули — раньше показывались все услуги салона, включая те, что этот мастер не выполняет, из-за чего можно было выбрать несуществующую для него услугу и всё равно увидеть свободное время (сервер теперь тоже проверяет эту связку и не покажет слоты/не даст записаться на услугу, которую мастер не делает). Сетка свободного времени в окнах записи/переноса стала скроллируемой внутри модалки (шапка и выбор услуги/мастера остаются на месте, скроллится только сам список времени) — раньше при большом количестве слотов окно могло не помещаться на экране без возможности прокрутки.

Формат телефона: везде, где вводится номер (регистрация клиента, анонимный визард `/booking`, ручное создание записи/очереди админом или мастером, создание мастера) — принимается только белорусский формат `+375XXXXXXXXX` (код страны `+375` и 9 цифр номера, 12 цифр в сумме). Пробелы, дефисы и скобки при вводе допускаются и просто убираются перед сохранением (`+375 29 123-45-67` и `+375291234567` — один и тот же номер), но итоговый формат проверяется строго — без `+375` или с другим количеством цифр сервер вернёт ошибку.

Подтверждение номера по SMS так и не подключено (по решению продукта) — вместо него теперь обычный пароль при регистрации. Это надёжнее, чем было (раньше кто угодно мог войти под чужим номером без всякого пароля), но сам номер телефона при регистрации по-прежнему не проверяется звонком/SMS — теоретически можно зарегистрироваться на чужой номер. Для реального продакшена стоит добавить подтверждение номера при регистрации.

## Локальный запуск

Нужны Node.js 20+ и Docker (для Postgres) либо своя PostgreSQL.

```bash
cd hairdresser-booking
npm install
cp .env.example .env        # при необходимости поправьте значения
docker compose up -d db     # поднять только Postgres, если нет своей БД
npx prisma migrate dev --name init
npm run seed                 # создаст админа и demo-данные (услуги, 2 мастера)
npm run dev
```

Джобу автоочистки (`scripts/scheduler.ts`) в `npm run dev` никто не поднимает — это отдельный долгоживущий процесс, для локальной проверки запустите вручную вторым терминалом: `npm run scheduler` (или разово `npm run purge:run`).

> Если у вас уже была развёрнута более ранняя версия проекта (без переноса записей), примените новую миграцию поверх существующей БД: `npx prisma migrate dev --name reschedule` (dev) или `npx prisma migrate deploy` (прод) — существующие данные не тронет, новых таблиц эта миграция не добавляет.

Открыть:
- `http://localhost:9999` — главная (Регистрация / Вход)
- `http://localhost:9999/register` — регистрация клиента (телефон, имя, пароль)
- `http://localhost:9999/login` — единый вход для всех (админ: email/пароль из `.env`, по умолчанию `admin@example.com` / `admin12345`; мастер: добавляется админом через `/admin/masters` — сид больше не создаёт демо-мастеров; клиент: телефон + пароль, заданные при регистрации)

Порты: Postgres — 9998 (хост) → 5432 (внутри контейнера), приложение — 9999.

## Деплой на сервер (VPS)

Если сервер архитектуры x86_64 с Docker и Docker Compose:

```bash
git clone <ваш репозиторий>
cd hairdresser-booking
cp .env.example .env         # задать реальный JWT_SECRET, ADMIN_PASSWORD, TZ
docker compose up -d --build
docker compose exec app npx prisma migrate deploy
docker compose exec app npm run seed
```

`docker compose up -d --build` поднимает три сервиса: `db` (Postgres), `app` (сайт на порту 9999) и `scheduler` (недельная автоочистка, см. выше) — все объявлены в `docker-compose.yml`, отдельно ничего запускать не нужно. Проверить, что джоба стартовала: `docker compose logs scheduler`.

Дальше приложение слушает порт 9999 — повесьте перед ним nginx/caddy с HTTPS (Let's Encrypt) и доменом. Без Docker — тот же процесс вручную: `npm ci && npm run build && npm start`, плюс своя PostgreSQL, переменные окружения и отдельный процесс `npm run scheduler` (например, под pm2/systemd) для автоочистки.

## Важные ограничения MVP (что стоит доработать перед реальным продакшеном)

Защита от двойного бронирования сделана проверкой внутри транзакции — для очень высокой нагрузки лучше дополнительно добавить exclusion constraint в PostgreSQL (`btree_gist` + `EXCLUDE USING gist`). Очередь (`WaitlistEntry`) обрабатывается вручную персоналом на странице "Очередь" — автоматического уведомления клиенту при освобождении окна пока нет (только когда его вручную запишут оттуда). Начисление бонусов — только поле в базе, правила начисления не реализованы. График мастера при создании через админку — фиксированный (Пн–Сб 10:00–19:00), точечные правки — через будущий UI или напрямую в БД. Ручное удаление записи в календаре админа/мастера (кнопка "Удалить") — это по-прежнему жёсткое удаление из БД без следа в архиве (архивируются только записи, которые прошли и попали под еженедельную автоочистку, а не удалённые вручную); если понадобится история и для ручных удалений, стоит либо архивировать их тем же способом перед `DELETE`, либо заменить `DELETE` на мягкое удаление (статус `CANCELLED`). Ограничение "мастер не может трогать прошедшие записи" проверяется по `startAt` и текущему времени сервера — если сервер и браузер в разных часовых поясах, возможны пограничные случаи у самой границы "сейчас".
